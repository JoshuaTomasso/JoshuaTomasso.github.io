Overview

Hidden Fangs is a Werewolf-style social deduction game for 4 to 16 players. Hidden roles are assigned at the start of each match, then play alternates between a Night Phase, where players with special roles act in secret, and a Day Phase, where survivors discuss and vote to eliminate a suspect. I built the whole game alone in C++. The server owns the match: clients submit requests, and the server decides what happens.

  • Server-driven match flow: Role Reveal, Night, Day and Voting, with win checks between phases
  • DataTable-driven role assignment across five roles: Werewolf, Medic, Seer, Villager, Mayor
  • Server-authoritative night action and vote submission, validated before anything changes
  • Session-based lobbies and a C++ settings framework (audio, graphics, display, key rebinding)
  • Tested with up to 4 simultaneous PIE instances for multiplayer validation

What I Worked On

Server-Driven Match State Machine

Each client tells the server when its player list is complete, and the GameMode starts the match once every expected player has checked in. A server timer then drives the loop.

  • Phase Loop — Role Reveal, then Night, Day and Voting on repeat, with a win check between phases.
  • Replicated Timing — The GameState replicates the current phase and its end time. Each client's timer bar computes its fill from that end time and the server clock, so no replicated countdown is needed.
void ACodeGameMode::OnPhaseTimerComplete()
{
    if (bGameOver) return;

    if (const ACodeGameState* CurrentGameState = Cast<ACodeGameState>(GetGameState<ACodeGameState>()))
    {
        switch (CurrentGameState->CurrentPhase)
        {
        case EPhases::RoleReveal:
            StartPhase(EPhases::Night);
            break;
        case EPhases::Night:
            ResolveNightActions();
            CheckWinConditions();
            StartPhase(EPhases::Day);
            break;
        case EPhases::Day:
            CheckWinConditions();
            StartPhase(EPhases::Voting);
            break;
        case EPhases::Voting:
            ResolveVotes();
            CheckWinConditions();
            StartPhase(EPhases::Night);
            break;
        default:
            break;
        }
    }
}

Phase state belongs on the GameState, not the GameMode. The GameMode exists only on the server, so anything clients need to display or react to has to live on an object that replicates.

Night Action Targeting & Validation

Clients never apply an action themselves. A night target or vote goes through a Server RPC on the PlayerState, and the server checks it before anything changes.

  • Server-Authoritative Submission — The server checks the phase, that both players are alive, that the player has not already acted, the Medic's and Seer's ability limits, that a Werewolf is not targeting their partner, and whether the role can act at night according to its DataTable row.
  • Error Feedback — When a check fails, the server bumps a replicated error counter and the client shows a notice through a RepNotify.
  • Private Results — Results only one player should see, such as the Seer's result and Werewolf partner names, go out through Client RPCs.
void ACodePlayerState::Server_SubmitNightAction_Implementation(ACodePlayerState* AbilityTarget)
{
    if (const ACodeGameState* GameState = Cast<ACodeGameState>(GetWorld()->GetGameState()))
    {
        if (GameState->CurrentPhase == EPhases::Night && bIsAlive && !bHasSubmittedNightAction
            && IsValid(AbilityTarget) && AbilityTarget->bIsAlive)
        {
            bool bCanVoteFor = true;

            if (this == AbilityTarget && CurrentRole == ERoles::Medic)
            {
                if (SelfProtectedCount >= 1)
                {
                    VoteErrorCount++;
                    OnRep_VoteErrorCount();
                    bCanVoteFor = false;
                }
                else
                {
                    SelfProtectedCount++;
                }
            }
            else if (WerewolfPartner == AbilityTarget)
            {
                VoteErrorCount++;
                OnRep_VoteErrorCount();
                bCanVoteFor = false;
            }

            // ... Seer ability limit, then the DataTable lookup:
            if (bCanVoteFor && RoleInfo->bCanActAtNight)
            {
                NightTarget = AbilityTarget;
                bHasSubmittedNightAction = true;
                OnRep_NightTarget();
            }
        }
    }
}

Server-side validation prevents client-side spoofing of actions, and private Client RPCs mean no client ever receives data about a role it isn't entitled to see.

Role Assignment & Hidden Role Reveal

Role definitions live in an Unreal DataTable, so rebalancing or adding a role does not touch the assignment code.

  • DataTable-Driven Roles — Each row holds the role's team, display text, icon, whether it can act at night, and whether it can announce itself publicly.
  • Scaled Assignment — The GameMode scales the Werewolf count with player count using a tunable ratio, caps it so Werewolves never start as a majority, unlocks the Medic, Seer and Mayor at configurable player counts, fills the rest with Villagers, and shuffles the pool.
  • Private Reveal — Werewolves are paired and each is told their partner's name privately.

Night, Vote & Win Resolution

  • Night — The server collects each Werewolf's target, picks the kill (randomly if the pack disagrees), applies the Medic's protection, and sends the Seer their result.
  • Voting — A player is eliminated only with the most votes and more votes than the skip option, so ties and skipped rounds eliminate nobody.
  • Mayor — Can reveal their role publicly, showing a marker over their character for everyone through a NetMulticast function and giving their vote extra weight.
  • Win Check — After every phase the server counts living players by team from the DataTable, declares a winner, and broadcasts the result.

Replicated Player State & Delegate-Driven UI

Each player's role, alive status, night target, vote counts and submission flags live on the PlayerState. Every RepNotify broadcasts a dynamic multicast delegate, so widgets react to changes instead of asking for them.

  • Manual RepNotify on Server — RepNotify functions do not run automatically on the server in C++, so the server calls them after changing a value, keeping a listen-server host's UI in sync with remote clients.
  • Runtime Player Lists — Night targeting and voting lists are generated at runtime, and live vote counts, the Werewolf partner's choice, role reveals and night results all use the same delegate pattern.
  • Order-Independent UI — Widgets that depend on the local PlayerState retry until it has replicated, so the UI does not depend on network arrival order.

Session-Based Lobbies

A GameInstance subsystem wraps the Online Subsystem session interface for creating, finding, joining and leaving lobbies, and reports each result through delegates.

  • LAN and Online — LAN sessions on the Null subsystem, internet sessions on platform subsystems.
  • Session Cleanup — Creating or joining while an old session exists destroys the old one first, then retries.
  • Lobby Setup — The host picks a lobby name and a player count from 4 to 16, passed to the match through travel options so the server knows how many players to wait for. Player names are sanitized for the connection URL and saved to a SaveGame slot.

Settings Framework

The pause and main menus share a C++ settings system built on CommonUI.

  • Audio & Graphics — Defined in DataTables. Audio uses Sound Classes and Sound Mixes with output-device switching. Graphics uses scalability settings, with an Overall option that flips to Custom when any single option changes. Both save between sessions.
  • Display — Monitor selection, window mode, resolution and frame-rate limits.
  • Controls — Enhanced Input user settings for key rebinding, with conflict detection, blocked applying until conflicts are resolved, and a prompt before discarding unsaved changes.

Notes

Gameplay Overview

Hidden Fangs is a social deduction game for 4-16 players. Each match alternates between a Night Phase, where players with special roles secretly act, and a Day Phase, where surviving players discuss and vote to eliminate a suspected werewolf. Villagers win by eliminating all werewolves; werewolves win by reducing the villagers to a number where they can no longer be outvoted.

Networking Architecture

Match logic is split across Unreal's gameplay framework by who owns the data. The GameMode runs only on the server, so it holds the rules. The GameState and PlayerState replicate to every client, so they hold what players need to see.

GameMode  (server only)
    ├─ Ready handshake and match start
    ├─ Role assignment
    ├─ Phase transitions and timers
    ├─ Night-action and vote resolution
    └─ Win conditions

GameState  (replicated)
    ├─ Current phase
    ├─ Phase end time and duration
    └─ Skip-vote count

PlayerState  (replicated)
    ├─ Role
    ├─ Alive state
    ├─ Night target
    └─ Vote counts

Architectural Lessons Learned

  • GameMode only exists on the server — any logic that needs to reach clients (Multicast RPCs, phase UI) has to live on GameState instead
  • RepNotify functions don't fire on the server in C++ — call them manually so a listen-server host sees the same UI as remote clients
  • Widgets that depend on replicated data should retry until it arrives, rather than assuming network arrival order
